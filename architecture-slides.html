Step 1 — Wake Word

WakeNet & Always-On Listening

🎙️ I2S mic → AudioInputTask

Raw PCM read from codec, fed to a single AudioEngine instance

↓

👂 WakeNet (ESP-SR)

Neural-net model running on-chip. Detects "Hi XiaoZhi" or custom wake word entirely offline. No cloud round-trip. Latency ~200 ms.

↓ (on detection)

🔴 AFE — Acoustic Front-End

FD AEC + VAD pipeline activates. Echo cancellation removes speaker bleed. VAD finds speech boundaries.

↓

📦 Opus encode → send queue

60 ms frames encoded to Opus, pushed to network send queue for WebSocket streaming

Two engine types

  • AfeAudioEngine — ESP32-S3 / P4 / S31: WakeNet inside full FD AFE, with AEC + VAD
  • LiteAudioEngine — ESP32 / C3 / C5 / C6: standalone WakeNet, raw mono PCM (no AEC)

Wake word audio cache

The last 2 seconds of PCM before detection are stored in a 64 KB PSRAM ring buffer so the server gets the full utterance including the wake word itself.

MultiNet (command words)

Optional custom wake phrases via MultiNet. AFE fetch output is passed to CustomWakeWord. Only available on S3 / P4 targets with PSRAM.

Button trigger

Physical button press also starts a session — bypasses WakeNet entirely. Useful in noisy environments.

Step 2 — Speech to Text

Streaming Audio to the Server

🎵 Audio format

  • Codec: Opus — low-latency lossy compression
  • Sample rate: 16 000 Hz (uplink)
  • Channels: mono
  • Frame duration: 60 ms per packet

🤝 Connection handshake

Device sends a hello JSON declaring audio params and feature flags (mcp, aec). Server replies with session ID and TTS output params (24 kHz).

📡 Transport options

  • WebSocket — binary frames for audio, text JSON for control
  • MQTT + UDP — MQTT for JSON, UDP for the audio stream

🔤 Server-side ASR

Server receives Opus frames and performs streaming ASR in real time. End-of-speech detected server-side. Transcribed text becomes the LLM prompt.

🔐 Auth headers

  • Authorization: Bearer <token>
  • Device-Id: MAC address
  • Client-Id: software UUID (NVS-stored)
  • Protocol-Version

📦 Binary protocol

Three wire versions supported. Default (v1): raw Opus frames as binary WebSocket frames. V2/V3 add timestamp and type metadata — used for server-side AEC.

Step 3 — LLM Response

Emotion-Aware AI Response

🤖 LLM backend

Claude Sonnet, reached through LiteLLM and the hai proxy (swap models in litellm.yaml). The server orchestrates the full ASR → LLM → TTS chain in a single session.

📨 Response structure

Server sends a tts JSON message containing response text, an emotion field, and session state signals before streaming the audio.

🧩 MCP tool calls

LLM may call device-side or cloud-side tools mid-conversation (lights, volume, home automation). Results flow back into the LLM context before the final spoken reply.

😊 Emotion → display

Emotion tag from the LLM response is mapped to an emoji on the OLED / LCD. Updated on every turn.

Step 4 — Text to Speech

Streaming TTS Playback

🔊 Streaming decode

Server synthesises speech and streams Opus frames as binary WebSocket messages. The device decodes and plays in real time — audio starts before the full response is received.

🎚️ Output audio

  • Codec: Opus (decoded on device)
  • Sample rate: 24 000 Hz
  • Channels: mono
  • Output via I2S DAC to speaker

📊 Audio pipeline

network → decode queue → OpusCodecTask → playback queue → AudioOutputTask → I2S DAC → speaker

⚡ Barge-in / interruption

While TTS is playing the mic and WakeNet stay active. A new wake word or button press interrupts playback immediately, cuts the audio channel, and starts a fresh session — natural conversation flow.

🔇 AEC during playback

On AEC-capable boards (e.g. ESP32-S3-BOX-3) the AFE keeps echo cancellation active during TTS playback so the speaker output doesn't trigger WakeNet.

🔁 Session end

Server sends a stop event when TTS audio finishes. Device transitions back to idle. WakeNet re-armed.

Extensibility

MCP — Model Context Protocol

Device and server both act as MCP endpoints. The AI can control the physical and digital world mid-conversation.

📦 Device-side MCP ESP32

  • Speaker volume control
  • LED colour / brightness
  • Servo / GPIO actuation
  • Battery & display info
  • Customisable wake words

☁️ Cloud-side MCP server

  • Smart home device control
  • PC desktop automation
  • Knowledge base search
  • Email / calendar actions
  • Custom tool integrations

Flow

LLM decides to call a tool → server dispatches MCP message to device (or external service) → device executes → result returned → LLM continues with tool output in context → final spoken reply.

Firmware Architecture

Software Layer Breakdown

⚙️ Application core

  • application.* — main event loop & protocol lifecycle
  • device_state_machine.* — state transitions
  • Callbacks scheduled via Application::Schedule()

🎵 Audio layer

  • AfeAudioEngine (S3/P4): WakeNet inside FD AFE, AEC + VAD
  • LiteAudioEngine (C3/C6): standalone WakeNet
  • OpusCodecTask: encode uplink / decode downlink

📡 Protocol layer

  • Transport-neutral Protocol interface
  • WebSocket implementation
  • MQTT + UDP implementation
  • JSON dispatch by type field

🖥️ Display & LED

  • OLED / LCD with LVGL
  • Emoji & rich expressions
  • Dynamic glyph push from server
  • LED strip via MCP

🔌 Board abstraction

  • 138+ board directories
  • Each exports one DECLARE_BOARD(...)
  • Chips: ESP32, S3, C3, C5, C6, P4
  • OTA-safe board identity

🤖 MCP server

  • Device-side MCP tool registry
  • Tool dispatch & result routing
  • NVS-persisted keys (stable API)
